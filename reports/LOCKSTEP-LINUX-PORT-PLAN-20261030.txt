HOW EACH MODULE IS PORTED
As the world hash: the shared logic stays in one header, compiled unchanged for Windows (its
preprocessed output must not change), with the constants, layouts and thread access per platform.
Each module gets checks in check_lockstep_gate_linux_sites.py, a white-box test on the ELF image,
an engine scenario where it can be emulated, then one live census.

causes is only known after a run, so the number to read after rank 1 is the motion count, not the
stamp count. Fixture ships and battles

LOADOUT ORDER
The Linux twin of native_gate_loadout_order (gate_loadout_order.h, stop reason 172 as on Windows). The sites, read on the
Linux executable, have Windows' shape: GetWantedSupplyOrders 0x1839ea0 calls the ware sort 0xb03680 at 0x183a470 and
the deployable, unit and ammunition targets 0x17e89d0, 0x17e86d0, 0x17e8bd0 at 0x183a537, 0x183a6d7, 0x183ac7f; the
ammunition target calls the existing-users walk 0x1def210 at 0x17e9063, which calls the pick 0x17b5f20 at 0x1defce1.
The result maps are X4's own tree with Windows' node layout. Two differences: the ware list has an 8-byte head, and each
rest (units in 0x1e9e3d0, deployables in 0x1df78e0) first gives the remainder to the macros that got nothing in their
input order (data order, left native); only what is left goes round the map in address order, from 0x1e9e7b0 and
0x1df8193, where a jmp leads to the shared rest arithmetic. Offline, test_gate_linux runs both native loops on the
executable's bytes against the stubs: the same counts in 'observe', the id order in 'canonical'; the engine scenario
protocol2_loadout_order gets the same map order and rest on two peers with reversed macro addresses. Not ported: the
stock in the rows (0).

ATTENTION
The Linux twin of native_gate_attention_all (gate_attention.h). The boot option of native_gate_attention_rng or
_initial_refresh installs the hook (stop reason 53 if it cannot, 54 on a failure, as on Windows). PeriodicAttentionRefresh
0x1465030 keeps the next due at +0x2d8 (Windows +0x2e0), reads the thread's time at fs:-0x2728 and steps the word at
fs:-0x2720 inline, then tail-jumps to SetAttention; its 5-byte prologue moves to a trampoline. Only 'all' is ported: each
saved or created object's first admitted call re-evaluates at once, and every call draws from (tick, key) with the word
restored after it. The fixture actors' own path and the diagnostic are not ported. Offline: a stand-in timer behind the
pinned prologue gives saved objects the same dues from different loading dues and words (test_gate_linux), and so do two
peers (protocol2_attention_all).

NAV KEY
The other drawer of win-sub4, the nav refresh NavigationController::vfunc33 (Linux 0x144a9e0), keyed on Linux only
(native_gate_nav_key, in gate_nav.h's existing vtable hook, no new site or stop reason). In an admitted frame on the
MoveWorker, a controller whose ship (+0x20) has a portable key runs with the thread's word seeded from (tick, key, class,
the ship's ordinal of the call in the tick, the time's bits), its own domain, and gets the word back after it. This
differs from Windows, which keys the same call inside actor_rng_all's ship scope, an umbrella over the whole ship Move,
its agents on the job threads and its weapons; that umbrella is not ported, so a Windows and a Linux client would key
this call differently. That does not matter while the platforms part at the first step. Offline: protocol2_nav_key
gives two peers with different natural words the same refreshed deadlines.

TEMPZONE ORDER (ready-to-build notes, not built)
The 1788 swap is Windows' warp/transit family (LOCKSTEP-CENSUS-20261028.txt): the pathing job threads race for the one
pending-tempzone slot, so which ship gets the next zone, and where it is centred, depends on thread timing. Windows'
native_gate_tempzone_order 'order' (lockstep_tempzone_order.h, stop reason 144) parks the slot at the pass release,
records the lookups that find no zone, and after the join grants the smallest request by (sector key, position) on
the MoveWorker. The Linux twin is on hold until the class C decision; these are its sites, read on the executable.
  zone request      0x12981b0, Windows FUN_140785db0, in Itanium order: rdi the returned reference, rsi the sector,
                    rdx the position, ecx create (Windows: sector, reference, position, create).
  request sites     zone switch 0x142efa0 (Windows 0xe88160): create=1 0x142fa2e, create=0 0x142fb34;
                    Agent_UpdatePathing 0x1444c70 (Windows 0xe8f250): create=1 0x14490be, create=0 0x1449609;
                    the region manager's cell request 0x12eb620 (Windows 0xee7290) at 0x12ec389, 'other' on Windows.
  pending slot      flag 0x3eb9730 (dword), zone 0x3eb96f0 (a reference), lock 0x3eb9700: X4's own mutex, lock
                    0x1a23650, unlock 0x1a236a0. A store copies the reference with 0x1fa4030 (Windows: inline counts
                    at +0x40/+0x44); a release is 0xa14540 on the zone +0x38 (Windows 0x96940); the slot is reset with
                    0x1dc8de0.
  active test       0x1cb3f40: false if the zone's byte +0x1e6 has bit 2 (Windows flags +0x1e4 bit 0x20000), else the
                    view word at +0x11c + index * 0x80 must have 0x10000 and not 0x40000, as on Windows. The index is
                    the thread's own: fs:-0x2620 selects 0x3e7742c or 0x3e77430. RunPass's clear uses the published
                    index from 0x12021e0 instead; Windows' twin reads the published view for every thread, and so would
                    the Linux one (0x12021e0).
  RunPass's clear   inlined into 0x13e35e0 (Windows 0xeabf00): 0x13e3d78 tests the flag; 0x13e4143..0x13e41a9 locks,
                    tests the zone with the published index, resets the slot (0x1dc8de0) and the flag (xchg 0), unlocks.
  a third clear     0x1dba740 (Windows 0x9ec1d0) resets slot and flag unconditionally under the lock (0x1dbbcd9,
                    0x1dbd5f5..0x1dbd620). Its callers are in the load and import code (0x1cdd4a0 = Windows 0x9ee7a0,
                    0x118a2a0 = Windows 0x8d2b80), so it should never run during a parked pass; the twin would count it.
New beyond the shared logic: the prologue hook with the Itanium order; lock and references through X4's functions; a
thread class for the pathing threads between the release and join that gate_path.h already owns (Linux has no
path_thread_class); the job context on Linux TLS (time fs:-0x2728, word fs:-0x2720); the park and grant at gate_path.h's
release and join, next to the travel snapshot's. Tests: a synthetic slot and lock with stand-in requests from two
threads, a two-peer engine scenario. Estimate 400-600 lines with tests.

A MIXED RUN
Bit-equal Windows with Linux is not a question of more keys: run 23 parts at the first step. A mixed run would now
measure how long logic holds with the rounding present, not where the platforms part. A 600-tick comparison of separate
runs on the same keys gives most of that without one. It would also need one key set on both sides, including 30 Hz
(a Linux twin exists in tick_hz and the path budget), the pass stride (unchecked) and gate.fast_reads (needs a stub).
Post-load IDs differ by about 400 slots across platforms, already on ships made before tick 1, so a second agreed cut
at the seal would not align them; it is not built, and nothing yet shows that it matters.

OPTION B: REIMPLEMENTING OR REDIRECTING CLASS C
No work started. Counts are static, from LOCKSTEP-CROSSPLATFORM-FP-INVENTORY-20261029.txt, whose simulation/other split
is a triage aid. Only the first-part figures above were measured in a game.

How many functions. These are upper bounds; the number that counts is not known yet:
  simulation functions with FP arithmetic      Windows 3,025 (71,839 operations), Linux 2,912 (84,533)
  of those with a high or medium twin          1,667 and 1,758; the other 1,358 and 1,154 have none yet
  high-confidence simulation pairs             1,377; 389 have equal operation counts, which does not prove equal bits
  proven constant-reciprocal rewrites          438 sites in 220 functions, 140 of them simulation
Measured: 574 of 10,281 ships differ after the first step, and only ships through tick 60.

How to bound it:
  1. Only functions that run. The static count includes everything the snapshot never reaches.
  2. Only functions whose result reaches synchronised state, with the tick-by-tick census as the stopping test.
  3. Possibly one side. Linux is strict IEEE, so Windows functions compiled strictly in Linux's expression order should
     give Linux's bits with Linux stock. Inference; it is proven only for Jolt, where X4's own Linux Jolt already matches
     our deterministic build. Windows-only work also means one class layout per function.
What does not shrink: a redirect works at function entry, so an inlined expression pulls in its enclosing function, and
394 simulation pairs differ in vectorisation. Every redirect is pinned to one build and must be rechecked on each game
update. All code must be our own. Jolt W1-W5 is this same work for one library, and Recast/Detour would need it too.
Inventory classes M, A, E, D and O are separate and still required.

Evidence to gather first, in this order:
  E1. Coverage: which of the 3,025 and 2,912 functions run in 600 ticks, by one-shot entry marks on each platform.
      This replaces the upper bound with a real count and shows how many have no twin.
  E2. First difference: for the ships that differ at tick 2 (0x7dcd0, 0x7dd7c, 0x7ddb8), inputs and outputs of the
      functions on their motion path, on both platforms, for one tick. Equal inputs with different outputs name a site.
      Repeated on a sample of ships, this shows whether the 1 ulp comes from a few functions or many.
  E3. Classify the E1 set: paired or not, equal or different profile, mechanical rewrite or real reimplementation.
  E4. Jolt's share: whether those ships have bodies in the Jolt step, from Windows' existing physics trace.
E1 and E2 each need a small diagnostic build; E3 is offline; E4 is one Windows run. A later pilot of one or a few
functions would be measured the way run 23 was: the count at tick 2, and the tick of the first position difference.

Results so far (approved as measurement only, no port):

      active scene steps 37 bodies, all keyed, and their state hashes are the same before and after every step (ticks
      1-5); the second scene is empty. The watched ships are at attention 2 and have no body. Ships near a camera do
      get bodies, so this is "not the cause here", not "never".

Count: about 870 Windows / 770 Linux functions run in this fixture's first 600 ticks. That is a lower bound for play:

Static result, before any run: with equal inputs the refresh's own arithmetic already gives equal bits on both
platforms. Windows' folded form 100 - ((x-x0)*99)/(x1-x0) equals Linux's 100 + ((x-x0)*(1-100))/(x1-x0) exactly
(1-100 = -99 is exact and negation commutes with rounding); the clamps agree, NaN included; M differs only for -0
and NaN. Checked on the executables' own code: the Windows test runs X4.exe's inlined +0x0 block and its M on
20,000 random inputs each, the Linux test runs the executable's L and M likewise; all equal ours (M except the
documented -0 case). So the one-ulp split at tick 2 has to come from an input of the refresh (comp+0x5d4/+0x5d8,
Windows +0x5f4/+0x5f8; the getters G0, G4; w, lane 2 of the owner's query vector; M's c), and FP_REDIRECT_ROWs give
every input's bits for watched ships on both platforms so the shadow run shows which. Unmeasured until that run.
