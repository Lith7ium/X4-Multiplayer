Disk persistence and SSH output
The frozen callback calls atomic_report, then emits an SSH checkpoint. The barrier
catches OSError/RuntimeError as disk failure. BrokenPipeError from the later output
is an OSError, so it overwrites an existing ssh_input_eof cause in memory; final
persist writes evidence_persistence_failed over the earlier durable reason.
An original synthetic reproduction confirms first disk=ssh_input_eof, memory and
final disk=evidence_persistence_failed. The005 report lacks the underlying syscall
exception, so it cannot retrospectively distinguish an actual disk error from this
reproducible output-error path. Missing local bridge evidence still means failure.

Correction in tools/dev/native_portable_ssh.py
CheckpointOutputError is distinct from disk-error types. After output failure,
the coordinator stops immediately and retains its first failure, or selects
ssh_checkpoint_output_failed if this is first. A separate true diagnostic field
of that name is persisted locally without another output attempt. Repeated abort
and final persist preserve both. Real disk errors, including that diagnostic write,
still follow the strict evidence_persistence_failed path; failed writes are never
claimed durable. The remote loop catches the distinct exception and stops Linux.

Atomic-write-before-checkpoint and Windows-output-before-Linux-output ordering
remain. No wire packet, native guard, receipt or validator is relaxed. Successful
reports retain their format; the additive field appears only on output failure.
The internal released counter can be set before persistence, so tests check actual
emitted packets and no GO rather than treating the counter as proof of delivery.
