NATIVE LOCKSTEP PILOTING: INPUT MAP, PILOT RECORD AND DRIVE PROTOTYPE
29 October 2026 | static analysis + offline prototype; no X4 launched, no live result yet

SUMMARY

Direct piloting under lockstep needs every client to simulate every player ship
through the SAME native motion path from the same per-tick control values. X4
flies the local player's ship through PlayerController (singleton input bank,
own embedded solver, integrated in VBI slot 3 after the pathing join) and every
other ship through its pathing Agent (Steering model, Agent solver, integrated
inside the pathing pass). Both paths end in the same per-axis velocity request
setter e5d380 on solver sub-objects with an identical layout, but they are not
the same simulation. A ship flown by PlayerController on its owner's client and
by the Agent elsewhere would diverge. The design is therefore "pilot by wire":
every player ship, including the local one, is flown on every client by its
Agent/Steering path, with only the value of the six existing Steering velocity
requests replaced from that tick's pilot record. The local PlayerController is
parked (native DeactivatePlayerControls) and never the motion authority.

Implemented (default off, stop reason 91): a 28-byte versioned pilot record,
local capture from the processed input channels, wire staging with explicit
capture tick t and apply tick t+d, a per-tick frame table published before the
pathing pass, request-value substitution for one designated saved ship per
slot, an optional owned park of native player controls, a per-tick receipt in
the declared state hash, status/STOP lines, and C/Lua unit tests. Not
implemented: device capture while native controls are parked, firing, boost and
travel semantics, and any presentation prediction.

1. MECHANISM MAP (exact build 9.00, X4.exe SHA256 19750a65...6891, RVAs)

  Agent_UpdatePathing e8f250 runs the model's vfunc +70 inside the pathing pass.
  SteeringFlightControlModel::Update ec7200 (vtable 2c4e9c8): r13 = Agent+340
  parameters; desired local linear velocity at model+1d0 and angular at
  model+1e0, clamped to the Agent's own limits: forward Agent+364, reverse lower
  bound +36c, x +370, y +374; angular axis 0 +37c, axis 1 +378, axis 2 +380
  (floats). Gains at solver+a258/+16528. Then the six request calls
  ec91c7/ec91e9/ec920b (solver+12cd0, axes 0..2) and ec922b/ec924d/ec926f
  (solver+6a00, axes 0..2, skipped when solver+31 is set), one step 1197fe0
  at ec92c0 and publication at ec92cc..ec9325.
  Axis semantics are shared with the player: linear 0/1/2 = local x/y/z (z

  38f0728..72b (primary fire callback 7e8ef0); autopilot target 2f4b7d8.

Wall-clock and presentation-dependent parts of local input
  Mouse steering accumulates main-thread mouse deltas between frames, so the
  per-tick amount depends on real time between gated frames; the response
  curve, dead zones, inversion and sensitivity are local settings; key press
  timing is wall-clock; throttle wheel/keys change 2f4b760 incrementally; the
  UI may run onUpdate up to three times per frame; open menus deactivate
  controls. All of these act before the processed channels. The record
  therefore carries the processed, ship-relative channels quantized once by the
  capturing client; every client, the capturer included, decodes the same
  integers. Steering in X4 is ship-relative (mouse offset from screen centre =
  rate request), so no camera transform enters the channels; free look and
  external cameras do not steer. Remaining scheme inputs (pitch-dependent
  autoroll, speed-dependent roll) read simulated state and stay deterministic.

2. PILOT RECORD v1 (28 bytes, little endian, 56 lowercase hex on the wire)

  0      version = 1
  1      mode bits: 0 flight assist, 1 boost, 2 travel, 3 target unmapped
  2..3   low 16 bits of the capture tick t
  4..17  seven int16 Q15: input x, y, z, pitch, yaw, roll, throttle
         (value = q/32767; -32768 invalid)
  18     buttons, low nibble: native trigger bytes 38f0728..38f072b
  19     zero (reserved: weapon group selection, v2)
  20..27 saved ID of the soft target, 0 if none; mode bit 3 when the target
         has no saved identity (runtime IDs never travel)
Decoding refuses any other version, unknown mode bits, a non-zero reserved byte
or high nibble, -32768 and an ID together with the unmapped bit. Apply tick =
capture tick + agreed delay d; the capture tick is reconstructed from its low
16 bits relative to the current tick. Blob multiplexing on the coming input
wire must be agreed with its owner; this record is self-identifying (byte 0).

3. PROTOTYPE (lockstep_pilot_inputs.h, lockstep_pilot_inputs_lua.h)

Arming (before loading, boot snapshot only; requires serial pathing and saved
identities; refuses the request observer, which owns the same entry):
  gate.pilot_inputs(manifest, source, delay, start, stop, suppress)
  manifest: 1..4 comma-separated 16-hex saved IDs, slot order; source 'script'
  (delay 0) or 'wire' (delay 2..30, start > delay); window start>=5..stop<=18000.
Hook: the existing e5d380 entry patch and thunk slot 2496/2528 of the request
observer, installed at the first live pass. request_dispatch routes to the
pilot only while it owns the entry. No new thunk space, no new native call in
the Steering path, no transform or order writes.
Per pass (path_release, before the pathing kick, MoveWorker): resolve each saved
ship (reverse saved->runtime once, Find ced70, component/controller/Agent
back-references, Agent+f80 solver), take this tick's records (script: from
slot and tick; wire: staged ring entry, capture tick must equal t-d), publish
the frame table. Missing or mismatched records stop with reason 91.
Workers: an e5d380 call returning to one of the six Steering sites, on a
driven slot's solver, with matching axis and tick, gets its value replaced by
record * the ship's own Agent limits (scheme above, single precision); all
other calls run the original once with unchanged arguments. Each substitution
adds lockstep_seed(PILOT_DOMAIN, tick, saved, stream, value bits) to an
order-independent per-tick receipt.
Lua (tools/dev/native_gate_probe.lua): per admitted tick, wire mode stages
s.inputs[slot] via gate.pilot_apply, captures and gate.propose()s the local
record; logs "PILOT_INPUTS tick=N ..." and appends PILOT_1:tick:applied:receipt
to the declared state hash; logs PILOT_PLAYER (occupied ship saved ID) at tick
1, optional PILOT_CAPTURE rows, and PILOT_INPUTS_STOP (also on abort).
Status fields: armed installed live source delay window slots frames
frame_tick frame_applied frame_receipt applied receipt calls missing late
unresolved no_solver bad_limits forced staged captures local_pending suppress
controls_owned open restore_open restored stage failures, and per slot
sN=saved/resolved/driving/player/angular_applied/linear_applied.
Local suppression (opt-in): at start-3 DeactivatePlayerControls once with
before/after ownership checks; every tick until stop the flag and counter must
still be ours (else stop 91); ActivatePlayerControls at stop+1 or on stop. A
foreign state is never touched; restoration reports restored=0 instead.
Capture (gate.pilot_capture) calls the pinned getters d8e5b0 (6c..71),
b09880, ea7600, ea7650 on the UI thread after this frame's native input update
and never writes input state. gate.pilot_pending lists this client's proposed,
not yet applied records with capture and apply ticks.
Pins (full function SHA256, checked before use; all match the image):
  e5d380/214, ec7200/10109, e95fb0/2048, Agent update e8f250/10613 (pre-patch
  bytes via the travel snapshot helper) and the other request-observer pins;
  ced70/184; capture 9fc550/277, d8e5b0/4712, b09880/91, ea7600/77, ea7650/56;
  suppression 179760/54, 175a00/66, d9cc30/53, d8d9d0/493.

Tests: test_lockstep_pilot_inputs.h (codec, script, mapping, manifest/config,
staging ring with late/duplicate/conflict/echo, frame table with missing/delay
mismatch/lost controls/unresolved ships, value substitution and pass-through,
receipt, dispatch routing through a stub returning to the real Steering site,
ownership/restoration with foreign states, pins against the actual image).
test_lockstep_gate.exe exits 0 with and without the pinned X4.exe; the full
build_native_gate.py --test --native-image suite passes; three new LuaJIT probe
tests plus the 54 existing probe tests pass.

4. DESIGNED, NOT IMPLEMENTED

Local ship under the delayed record: park the PlayerController (lever above),
put the local player's ship in its own slot, and drive it on every client with
the same substitution. Parking removes the native flight input contexts, so the
input bank is no longer fed and capture reads zeros. Capture while parked needs
one of: (a) a mod-owned device sampler at the gate boundary (raw input/XInput)
with its own bindings; (b) keeping the flight contexts requested by another
requester without letting the controller retake motion authority (needs the
d88710 activation gating); (c) an autopilot-like regime, where GetTransform
already follows the Agent banks, if input processing stays live there. Each
needs a read-only live observation first.
Assist off: the scheme uses relative accelerations; the Steering path exposes
only velocity requests. Prototype applies the assisted mapping (the record
carries the assist bit). Boost/travel: full forward is forced like the scheme,
but the driven Agent's limits do not change until its own native travel/boost
state does; travel needs the per-ship native activation (ea7650 reads the ship).
Fire: buttons and target are carried, not applied. Firing for remote players
needs per-ship gun ownership, aim and the launch RNG scope already proved for
the singleton (NATIVE-PLAYER-CONTROLS-20261027.txt).
Weapon groups and match speed: reserved for record v2.

5. RISKS

Input latency: the local ship responds d ticks late (d>=2 on the current wire;
2 ticks = 33 ms at 60 Hz plus wire time). See the prediction section.
AI interplay: substitution happens only while the ship's Steering model runs.
AI orders may switch to Spline (docking, travel), Forced or Highway models,
re-target, or complete orders after the solver (e88160); weapons and turrets
stay AI-controlled. Applied counts in the receipt show this; it is the same on
every client if the world is. A pilot slot needs an exclusive authority/order
lease (NATIVE-PILOT-AUTHORITY-DESIGN-20261027.txt) before real play.
Collision avoidance: the replaced Steering request included avoidance; driven
ships fly straight into obstacles (deterministically).
Attention: low-attention ships take cheaper/less frequent updates; pick ships in
the player's zone. Ship death or unresolvable IDs are counted, not driven.
Parked controls: whether d93440 still publishes the player ship after
DeactivatePlayerControls, and when the queued Steering model becomes active,
is unobserved. UI code that reactivates controls stops the run (reason 91).

6. FUTURE: LOCAL PRESENTATION PREDICTION (no code)

Separation: the record carries its capture tick; the apply tick is capture+d;
gate.pilot_pending exposes this client's unapplied records (capture, apply,
bytes). A predictor needs exactly these d records plus the last simulated
state of the local ship.
Where presentation is derived: ship transforms are read through controller
vfunc6 GetTransform (NavigationController::GetTransform ea5a70 ->
GetTransformImpl ea5a90 from the pathing read bank; PlayerController override
d8a680), velocity vfunc7 ea6280. These serve simulation and rendering alike and
must not be changed. Camera controllers run in slot 3 (e.g. Player vfunc674
7113e0) and Camera::vfunc3 983160 / vfunc5 984fd0 write view data into the
producer half [idx^1] of the render double buffer on the MoveWorker; slot 10
GameRender::Move 121c1f0 builds render lists into the same half (draw-item
pushers f47870, f47360, f46fd0, f47260, f47170); the main thread renders [idx]
(RenderView f874c0). A prediction offset belongs on the producer-half data of
the local ship and camera after slot 3 (empty VBI slot 7 data-only handler, or
camera/view output), never on components, controllers, pathing banks or the
solver, and must use the render-side RNG split, never the simulation RNG.
What diverges while the offset is non-zero: projectiles, beams and muzzle
flashes start from the simulated gun transforms; aim and target lead are
computed from simulated position/velocity; HUD target leads, crosshair and
UI positions read simulated state through FFI; collisions, docking prompts and
proximity triggers happen at the simulated pose; positional audio and other
players' views follow the simulation. Mouse steering is ship/screen-relative,
so a predicted camera does not change the meaning of the captured channels.
The offset must converge to zero as each pending record is applied.
