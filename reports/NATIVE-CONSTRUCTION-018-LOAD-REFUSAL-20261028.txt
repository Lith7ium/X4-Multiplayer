Source diagnosis
----------------
registry_creation_configure requires !boot_phase before its already-configured
branch, both under creation_lock and under registry_creation_lock. The successful
production lua_load_requested call sets boot_phase from0 to1; boot_next advances
only1->2->3. Thus this phase predicate necessarily refuses a saved-game UI
reattachment after LOAD_REQUEST. Other predicates were not individually logged,
so this is a sufficient cause, not a claim that all other checks passed.

creation_rng_configure independently has the same unconditional phase0 predicate
before its already-started ACK branch. Fixing only registry configuration would
leave the second refusal. Existing C ACK text and Lua/Python readers also require
phase0, so removing the native check would produce untruthful evidence.

The accepted reattachment tests recreated Lua state but did not cross the native
Load transition; phase1 was deliberately a negative case. A new versioned contract
must distinguish phase0 initial installation from immutable, owned, zero-activity
reattachment after Load. Production lua_load_requested/boot_next and two separate
Lua VMs must be exercised together, with original identity, ownership, activity,
failure, STOP and restoration-debt refusals preserved. No source repair is part
of this report.

The first Lua configuration refusal precedes finish. Native RNG stop requires two
completed scopes; aborting with zero scopes can produce CRNG_SCOPE/trace error8.
It is not a native constructor failure. The reloaded Lua VM fails before creating
its RNG draining closure, explaining why no RNG STOP line is emitted even though
native finish invokes the stop path.
