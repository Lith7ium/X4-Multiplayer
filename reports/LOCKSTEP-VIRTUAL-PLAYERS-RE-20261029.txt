29 October 2026 | offline static analysis of the pinned Windows X4.exe 9.00
(SHA-256 19750a65...6891, base 0x140000000; RVAs below) + step 1 built (default
off); live test A analysed and step 2 (slot 1 through X4's own path) built, default
off, sections 11-13; step 3 spike (a second U::Player: construct built, seat
designed), section 14; round 3 (live results, map fixes, slot 1's view in the
record), section 15; round 4 (round 3 results; slots 2..N through X4's own path,

launched here. [F] = read in the binary (decompiled or disassembled,
function pinned where it matters); [I] = inference; [P] = earlier report or run.

GOAL (user): every player ship flies with the game's own player systems. Each
client "thinks" every player is player 1: in the simulation, on every client, in
a fixed slot order, X4's own per-frame player control path runs once per slot k
with the player-side state swapped to slot k's block and the input replaced by
slot k's recorded input. Slot 1 runs the same way. Local presentation (HUD,
camera) belongs to the local-player work (contrib/ferrite-local-player).

0. SHORT ANSWERS

- The path: input dispatch (VBI slot 4, MoveWorker) -> stock handlers write the
  process-global input bank 0x2f4b720..0x2f4b998, the Universe player's fields or
  the occupied ship -> component tree Move (slot 3: Player::Move 7113e0,
  PlayerController::vfunc33 d97e80, weapons' PlayerShootController 7e8bc0) ->
  PlayerController::Update d95180 (slot 3, after the pathing join): device stage
  (raw bank -> processed channels) then sim stage (control scheme -> requests ->
  own solver d93440 -> authority d8dd50 -> publish). Activities (travel, scan,
  long-range scan, SETA) are MD: the handler signals the player entity and
  md/modes.xml calls set_player_activity (710ed0), which engages the drive.
- All of it runs on the MoveWorker. The input state is mostly process-global
  (one bank, not per controller); the rest is the Universe player's fields and
  the PlayerController object of the occupied ship.
- It can run for a ship the player entity does not sit in only if (a) that ship
  has its own PlayerController (Controllable::vfunc1074 creates one) and (b)
  "the player" resolves to that ship: 9fc550 and about 15 other accessors walk
  the singleton player's parent chain, d95180 itself checks the player's zone.
  1,041 functions read the singleton (*(0x143d198f8)+0x230); 68 of them are in
  the direct-call closure (depth 3) of the per-frame control path.
- A per-slot swap is cheap and allocation-free (about 1.1 KB of globals and
  player fields, memcpy) if it happens only on the MoveWorker while no other
  simulation thread runs (gate serial pathing gives that from path_release on).
  The hard parts are identity (who "the player" is) and the MD-driven
  activities, not the bytes.
- Recommended: N player entities (one U::Player per slot, seated in its ship
  through the stock control-position path), the scope swaps the singleton
  pointer plus the global block, and the input record is the stock dispatch
  stream (kind, id, value) replayed through the stock dispatchers in the slot's
  scope. Fallback: one entity, accessor redirection. Section 6.
- Built: step 1, native_gate_virtual_players='observe' (default off, read-only):
  the block map with classes, pins, swap/scope primitives (offline-tested), a
  per-frame observation of the canonical player's block and a census of every
  registered input handler. Section 8.
- Built since: the map corrected from live test A (camera pick is DEVICE,
  neighbours of the guard pages named; section 11) and step 2,
  native_gate_pilot_stock (default off, stop reason 155): slot 1 flies with X4's
  own player control path on every client from client 1's recorded stock
  dispatch stream. Section 12; live tests wanted in section 13.

3. CAN THE PATH RUN FOR A SHIP THE PLAYER DOES NOT SIT IN? [F, I where marked]
- A ship needs its own PlayerController. Creation: Controllable::vfunc1074
  4500a0 (allocates 0x19520, d83ae0 from the NavigationController, installs via
  vfunc 0x19e8, then 6e1e00, UI refresh). Its only caller is the take-control
  path 70e630 <- 716670 (control position activation: ControlPositionAction
  vfunc2 35b8a0, Player::vfunc76 7052f0, 7142a0, 11f553f): reparent the player
  into the control room (3d8420), player+0x6ab8 = position, 7aa710(ship,
  player), Gravidar 10b2e80(*(0x6cf1650), 0, ship), HUD weapon pointer, then for
  the pilot position 70e630: release the previous controllable (70e940 ->
  vfunc1075), new->vfunc1074, travel activity restart.
- d95180 runs only for the controller 9fc550 returns, and 9fc550 needs: the
  singleton player's vfunc 0x1c50(0) true, a non-null entry in player+0x308..
  0x310, and the player's nearest Controllable ancestor equal to that entry.
  d95180 also requires the player's zone == 0x6b661e8. So the path is tied to
  where the player entity physically sits.
- The binding d84c20 resets the global bank and reads the singleton (camera
  head controller d895a0 checks the player too; it only adds one if the camera
  has none, so a second controller does not touch the camera [F]).
- Everything that asks "the player's ship" walks the singleton: 9fc550, 9f7860,
  9f7a40, 9f9250, 55b150, 9f9590, 9f7950, 9f7c20, 9fcd70, 9fccd0, 9f7b30,
  9f7d30, 9fcf00, 9fcfd0, 9f76e0, plus inline walks (d95180's zone check,
  70e630, d895a0). 1,041 functions reference 0x143d196d8; 542 of them are under
  400 bytes; 68 lie in the depth-3 direct-call closure of d95180, vfunc33,
  vfunc34, the flight/player/weapon handlers and 9fd120/9fd330.
- [I] Nothing in the flight model itself (d93440, solver 1197fe0) is
  player-ship-only: the solver is shared with Steering, and +0xd1 is not a
  player flag. The player-only parts are the identity checks above, the global
  bank, the trigger sweep / avoidance through the singleton's ship (d93440,
  d96dc0) and Gravidar's player-ship registration.

4. WHAT A SAFE PER-SLOT SWAP NEEDS
- Thread/phase: swap only on the MoveWorker and only while no other simulation
  thread runs. With the gate's serial pathing (path_release joins the pass
  before slot 0 continues) the component tree phase, d95180 and slot 4 run with
  the pathing workers idle [F lockstep_gate.c]. Physics jobs run inside Scene::
  Step (after d95180); the main thread renders concurrently (presentation only).
- Readers off the MoveWorker must never see a swapped value: PlayerController
  vfunc6/7/10 (inlined d8dd50) and the getters are called from pathing/physics
  for neighbours. They need per-controller answers that do not read the swapped
  globals (the pnat module already routes vfunc6/7/10 and d8dd50; the same
  routers would answer from a per-slot authority snapshot taken at the end of
  each slot's d95180 scope).
- Bytes: SIM (and with the dispatch-replay record also DEVICE) regions plus the
  identity (singleton pointer or accessor redirection), exchanged in place
  (step 1's vpl_exchange: no allocation, no temporary block). Never swapped:
  LOCAL (0x2f4b7e0/7e4, 0x2f4b829: this client's menus), SHARED (MD locks),
  CONFIG. The reentry flag 0x38f4db4 must be 0 at enter and leave.
- Identical on every client: fixed slot order 1..N, fixed points in the frame,
  slot stores initialised by the stock bind (d84c20 inside the slot's scope),
  OPTION values per slot from the session config (not the local machine).
- Per-call, not per-thread: a scope must wrap exactly one stock entry (one
  d95180 call, one vfunc33 call, one replayed dispatch, one shoot decision), so
  nothing between two entries sees a foreign slot.

5. WHAT BREAKS (or must be handled) [F unless marked]
- Activities are MD: md/modes.xml listens on player.entity and acts on
  player.occupiedship, set_player_activity writes the singleton. A slot's
  startactivity must reach a per-slot equivalent (section 6).
- Presentation inside simulation handlers: UI feedback sounds/voice
  (1257950/1257a20/1257b00, 14e8ec0), Lua event sink notifications, cockpit
  tint and sounds from modes.xml, HUD weapon pointer in 716670. Replaying slot k
  on client j plays slot k's feedback on client j unless filtered per scope.
- Camera-dependent player state: 717ed0 writes player+0x6c88 (target) from the
  local camera every frame; 7e8650 (aim) reads it; Player::Move checks the camera
  at 713037 (camera+0x868). With per-client cameras (local-player work) this is a
  desync class of its own, independent of virtual players.
- Gravidar: 716670 registers the ship as the player's radar ship; slot ships
  were registered as NPC units at load (10b2820 sets the player flag only for
  the occupied ship). [I] map discovery stays slot 1's.
- Per-machine options alter simulation: autoroll 0x2f4b9be, stop ship in menus
  0x2f4b9bf, aim assist 0x2f4b9c0/9c4, collision avoidance 0x2f4b9cc, boost
  toggle mode 0x38f52d7, mouse/joystick curves in *(0x6cf1538).
- The SPACE context (menus, map) toggles flight control per client today
  (d88710 -> d9c250/d9c590: Steering model, AbortPathOrder, transform adoption).
  Per slot it must come from the record.
- AI pilot of slot ships: [I] the stock take-control path replaces the NPC as
  controlling entity (7aa710); while flight control is on the controller owns
  motion and AI flight orders do not move the ship; AI scripts still run.
  Unverified at run time.
- Allocations/events are fine if identical: highway effects, activity events,
  boost feedback allocate and post in the same order on every client when the
  same slots replay the same inputs. Not fine: anything keyed on the local
  client (feedback, camera).
- Player statistics (69a490) and "player owned" UI state accumulate per entity.

6. DESIGN: N VIRTUAL PLAYERS

Identity, option 1 (recommended): one U::Player per slot. The Player ctor 6fa8e0
already repoints the singleton (Universe+0x230 = this, ref-counted) whenever a
Player is constructed (ComponentFactory::Create 8e0250 -> 6fa0b0; 8e2ec0 ->
6f8fd0, [I] the load path). A scope for slot k stores the singleton pointer and the
global block and loads P_k and slot k's block; every reader (all 1,041 functions,
inline walks included) then sees P_k with its own seat, posts, assist, activity,
aim and target. P_k is seated in ship k through the stock control-position path
716670 inside scope k, which creates C_k through vfunc1074 and binds it
(d84c20 resets slot k's bank). Open: creating extra Player components (factory
call at a gated tick vs. snapshot injection), Player::Move for P_k (wrap U::Player
slot 674 into scope k), MD that listens on player.entity (activities).
Identity, option 2 (fallback): one entity; the scope swaps the player-field
regions in place and redirects the accessors listed in section 3 plus the inline
zone check. Larger hook surface, events posted to the one entity are not per
slot, activities would need the same MD adapter.

Input record (recommended): the stock dispatch stream. On the capturing client
the three dispatchers (already re-stated by pnat) keep presentation/UI ids local
and record every control id as (kind, id, value) in dispatch order, plus SPACE
activation edges and d88a10's three outputs per tick (the only control input
that is not a dispatch: cursor position). At apply tick t+d every client, for k
in slot order, opens scope k and replays slot k's events through the same
multimap walk (all registered handlers of that id, stock order), then d95180
for C_k runs with its full device and sim stages (d88a10 answers from the
record inside a scope). Device state (key flags, ramps, timers) is then per
slot too, and no handler needs splitting. Per-slot settings (OPTION class, the
config/input-object fields the device stage reads) are fixed per slot at
