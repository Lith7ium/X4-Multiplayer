Actual construction diagnostic, 27 October 2026

Scope: one explicit stock structural-base module, a real station build task,
and a real builder DeployToStation order in two disposable native games.
This is separate from already-operational account fixtures. No instant completion,
build-speed override or replay of a host's module state is used.

The admitted input family uses 0x49 for a shared station plan and 0x4a for the
second logical player's builder. Both input encodings are checked before effects.
The station plan is locked while pending. Requests have deterministic fixture
tickets and expected revisions. Enqueueing returns PENDING; an acknowledgement
is emitted only after MD observes the actual expansion task, its single expected
module macro, or the actual native builder order. Unexpected/duplicate ACKs and
timeouts fail closed. A builder request requires acknowledged plan creation.
This small protocol is not the future shared command dispatcher or a PvP faction
permission implementation.

The canonical plan digest covers the selected module, zero position/rotation,
absence of equipment/connections, default construction method and unpaid plot
dimensions. The one-module fixture uses struct_arg_base_02_macro; its inspected
stock default production time is 53 seconds. This bounds the first actual-build
test without claiming the module represents a complete usable station.

The build storage is supplied with exactly the resources reported by the native
build task. Seeding is explicitly logged, separately from construction consumption.
It is not a trade/purchase or proof of credit deduction. Each resource's seeded and
remaining counts are hashed; resource creation beyond that baseline is refused.
The test retains the native task creation/processing, builder assignment/deployment,
module total and operational counts, station operational state and native progress.
Builder order queues and exact round-trip numeric progress are captured each frame.
The new builder's exported position/rotation is hashed every frame too; it is
outside the inherited battle fixture and could otherwise diverge during travel
before its deployment/progress counters expose a difference.
MD measurements are sampled every 30 ticks, with source and observation ticks;
missing/stale samples are failures. Hashes use logical fixture handles, never
runtime component, task or order IDs.

Acceptance requires two acknowledged requests, a previously empty station,
observed intermediate native progress, an actual DeployToStation order, the builder
assigned and deployed, a completed module, and full resource consumption. Matching
pending requests alone cannot pass. Independent evidence tests reject wrong plan
ACKs, missing progress/completion and impossible resource balances.
